# Bouncer Core M009-A / Plan 047 — OTRv3 Opaque-Carriage and Multi-Client Invariants

Status: closed

Architecture authority:

Primary class: privacy invariant + protocol compatibility

## 1. Objective

Make i2pr-irc demonstrably transparent to classic OTRv3 traffic without implementing or terminating OTR cryptography.

The product claim is:

**OTRv3-transparent bouncer transport compatible with OTR-capable IRC endpoints.**

It is not:

- a bouncer-side OTR implementation;
- an OTR cryptographic library;
- a claim that ordinary clients gain E2EE automatically.

## 2. Endpoint boundary

The local downstream IRC client and remote IRC client are OTR endpoints.

i2pr-irc must never own:

- OTR private/identity keys;
- fingerprints/trust;
- SMP state;
- instance/session keys;
- ratchet/DH state;
- decrypted message text.

No OTR production dependency is added.

## 3. Wire corpus

Build a bounded test corpus representing classic OTRv3 transport forms:

- query/start messages such as ?OTRv3?;
- encoded OTR protocol bodies beginning ?OTR:;
- fragmented OTR bodies;
- whitespace capability tags appended to plaintext where legal in IRC trailing parameters;
- payloads containing punctuation/base64-like material;
- near-line-limit fragments.

Use public protocol/reference shapes or synthetic structurally representative values; do not embed private test keys.

The bouncer need not validate OTR syntax. Corpus labels exist only in tests.

## 4. Byte-preservation invariant

For OTR-bearing PRIVMSG/NOTICE trailing parameters:

- body bytes received from one IRC side are preserved through parse/mediation/render to the other side except transformations required by IRC framing itself;
- no trimming of meaningful trailing spaces/tabs inside the trailing parameter;
- no UTF-8 normalization;
- no OTR-specific unescaping/reformatting;
- no concatenation of fragments;
- no fragmentation generated by the bouncer.

If the generic IRC wire layer currently normalizes legal trailing bytes in a way that breaks the corpus, fix the generic wire representation rather than add an OTR special case.

## 5. IRC tags and capabilities

Existing IRCv3 tag mediation may add/remove IRC message tags according to negotiated policy.

It must not alter the OTR payload body.

Examples to qualify:

- server-time added/preserved around an OTR-bearing message;
- account-tag filtering;
- labeled-response/echo behavior where relevant;
- client-only tag policy.

OTR does not become an IRC capability and must not change upstream CAP fingerprint.

## 6. Replay semantics

Outgoing OTR-bearing PRIVMSG/NOTICE is ordinary ambiguous user chat.

Therefore:

- it remains NonReplayable;
- reconnect never automatically retransmits an OTR data/AKE/query frame whose delivery is ambiguous;
- OTR state recovery is an endpoint responsibility.

Do not add "OTR handshake is safe to replay" heuristics.

## 7. Multi-client behavior

With several local clients attached:

- incoming OTR payload follows ordinary target/session fanout rules;
- every eligible session receives the same opaque body;
- the bouncer does not inspect OTR instance tags to select a client;
- an OTR-aware client may consume it and an unaware client may display opaque text;
- no per-session OTR state is created in the bouncer.

One client's OTR capability/use must not alter the upstream IRC capability fingerprint.

## 8. History behavior

If history is enabled:

- store the exact opaque IRC event/ciphertext received by the bouncer;
- no decrypted plaintext exists in Store APIs;
- replay returns the stored ciphertext;
- FTS may index the opaque text as ordinary message content, but no claim of meaningful plaintext search is made.

Do not build an OTR parser merely to suppress/index special cases.

M008's SQLCipher protects that ciphertext and its index at rest when encrypted-store mode is enabled.

## 9. Anonymity/security mediation

Existing CTCP/DCC/client-tag anonymity policy remains in force.

OTR's ?OTR... body is not CTCP and must not be rejected merely because it is cryptographic-looking opaque text.

No diagnostic/log path should begin logging message bodies in order to debug OTR.

## 10. Tests

At minimum:

- inbound query body exact;
- outbound query body exact;
- encoded data body exact;
- fragment sequence remains distinct/in order;
- trailing whitespace-tag preservation;
- near-max IRC line OTR fragment;
- OTR body under server-time/account-tag mediation;
- simultaneous modern/legacy/passive sessions receive body according to ordinary fanout;
- reconnect drops ambiguous outbound OTR chat rather than replaying;
- history append/replay yields ciphertext exact;
- source/dependency scan proves no libotr/libotr-ng/custom OTR crypto module.

## 11. Rust-only/unsafe boundary

Do not introduce:

- libotr FFI;
- libotr-ng FFI;
- unsafe code;
- native OTR helper linked into the product.

Reference libraries may later be used as external interoperability or corpus generators.

## 12. Acceptance criteria

Plan 047 closes when:

1. representative OTRv3 bodies survive the bouncer byte-exactly;
2. trailing whitespace/fragments are not normalized destructively;
3. no OTR cryptographic/session state exists in the bouncer;
4. multi-client behavior remains ordinary opaque fanout;
5. outbound OTR chat preserves non-replay semantics;
6. history contains only observed ciphertext;
7. no upstream capability fingerprint change is introduced.

## 13. Stop conditions

Stop for corrective/ADR if:

- preserving OTR requires bypassing IRC parser safety bounds;
- a client requires the bouncer to own OTR keys/session state;
- generic wire changes would violate IRC framing invariants;
- multi-client correctness requires interpreting OTR instance tags;
- an external native crypto dependency appears necessary.
