# Workspace overview

The workspace separates `i2pr-irc-wire` (bounded protocol bytes), `i2pr-irc-core` (IDs and network/time contracts), `i2pr-irc-store` (bounded owned SQLite worker and typed durable operations), `i2pr-irc-testkit` (deterministic short-I/O stream), and `i2pr-irc-runtime` (Tokio composition). `i2pr-irc-fuzz-smoke` feeds bounded arbitrary byte inputs through both wire entry points.

Only the runtime consumes `I2pStreamProvider`; core, wire, and store own no concrete sockets or resolver. The store owns one SQLite connection on its own thread behind a bounded queue, so blocking database work never runs on a network owner or downstream task, and it never persists live ObservedState. The catalog owns many Networks independently, and each attached local client is its own task rather than a branch of a shared loop. History is a durable, bounded journal with monotonic per-client cursors, and legacy playback advances a cursor only after the session writer confirms the bytes reached the socket. See [durable storage](storage.md), the [identity model](identity.md), [network and session ownership](network-ownership.md), and [history, cursors, and playback](history.md), and [capabilities and response routing](ircv3.md), and [CHATHISTORY and read markers](chathistory.md), and [history search and indexed references](history-search.md), and [downstream IRCv3 protocol polish](downstream-protocol.md). M001, M002, and M003 are evidence-closed, as is Corrective 013, which repaired five post-closure defects in server-time preservation, CHATHISTORY grammar, MARKREAD semantics, upstream queue integrity and downstream fanout ordering without weakening the invariants M003 closed. M004 is closed: CTCP/DCC mediation and a deny-by-default client-tag policy keep local clients from being prompted to describe themselves ([anonymity protocol mediation](ctcp-dcc-policy.md)), live response routing keeps one client's correlated reply away from the others ([response routing](response-routing.md)), a process-wide reconnect scheduler stops a router restart from becoming a retry herd ([reconnect budget](reconnect-budget.md)), and a bounded ledger makes resource recovery measurable ([resource accounting](resource-accounts.md)). The runtime owns many Networks independently, each with one live owner across connection generations, and any number of local client attachments per Network — so upstream registration, liveness, and retained state survive local-client absence, and one client's pressure reaches neither the Network nor another client. Observed channel, member, and mode state is driven by advertised ISUPPORT values and is projected only when it is truthful. Durable intent is committed before the upstream bytes that realise it, and converges through a bounded reconciliation set when that enqueue is refused. It remains short of a complete daemon and has no concrete router integration.


M005 planning authority is Research 006 and ADR-0003. The mature-feature line begins by adding a bounded process RuntimeController and pre-bind DownstreamAdmission while retaining NetworkOwner as the sole owner of bound sessions and upstream generations; see control-session.md. Plans 020-028 decompose the milestone. Plan 020 landed the bounded `RuntimeController`, the pre-bind `DownstreamAdmission`, the one-shot `PreparedSession` transfer, and schema 3. Plan 021 landed the typed `DesiredChannelRecord`, schema 4's bouncer-owned `detached` flag, and the detach/reattach transitions: a channel can be hidden from every attached session while the bouncer stays joined upstream and keeps collecting bounded history, and the policy survives restart because it is durable rather than derived. Plan 022 landed schema 5's `auto_away` and `keep_nick` policy (both migrated disabled), per-session active/passive classification with `draft/pre-away` mediation, an owner-scoped manual-away that survives reconnect, a bounded deterministic nick-fallback sequence answered inside the registration window, and MONITOR-assisted or ISON-probed keep-nick reclaim that a client attaching cannot make poll faster; see [presence and preferred-nick policy](presence-and-nick.md). Plan 023 landed the `soju.im/bouncer-networks` draft and the local `BouncerServ` administration service: a client that has never heard of this bouncer can now discover what Networks exist, select one before registration completes, and administrate Networks, channels, and presence policy through typed control; see [bouncer networks and administration](bouncer-networks.md).
